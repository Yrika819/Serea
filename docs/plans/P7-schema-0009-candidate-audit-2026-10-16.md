## PROPOSED details that block canonical promotion

The SQL contains provisional numeric caps, timestamp limits, retention and renewal bounds, quota accounting, FTS tokenizer choice, lineage/supersession behavior, Forget operation/tombstone lifecycle, quarantine removal mechanics, and Owner epoch/state fields. They are prototype values derived from the existing fixture, not Owner-approved policy. OwnerId issuer/authentication and a production authority source are absent. The candidate does not prove rollback-resistant Owner authority, production migration/backfill safety, or Gate D.

Therefore the file is not named `0009.sql`, is not added to `Migrations::embedded()`, and is not evidence that Production Memory is enabled. Canonical 0009 remains blocked pending resolution of those exact policies and an independent migration/security review. P8 work depending on these relations must remain development-only and stacked on this candidate branch.

## Checksums and repeatability

The test reads the source bytes at compile time and stores/verifies the checksum generated by the existing migration checksum routine inside the disposable database. It does not reserve a production checksum or alter the ordinary catalog. A future accepted 0009 must be independently frozen and checksummed after the policy blockers close.
