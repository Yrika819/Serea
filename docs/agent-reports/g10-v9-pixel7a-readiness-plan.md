## Acceptance packet required before device scheduling

Prepare one immutable packet for the exact candidate source and APK. Each result must carry source SHA, tree SHA, run/attempt/job, artifact ID, ZIP and APK SHA-256, and a status of `PASS`, `FAIL`, `BLOCKED`, or `NOT_RUN`. Never carry a result from a different source or package forward as a pass.

1. **Package identity and coexistence.** Record the Owner-ratified Beta ID and Demo ID. Current code candidates are `app.serea.android.beta` and `app.serea.android.demo`; this is not ratification. Prove the two IDs can coexist, launch independently, and keep separate app-private databases, preferences, files, credentials, and model directories. A disposable profile and synthetic data are required for install tests. Confirm that installing or updating one package never overwrites the sibling package or its private data.
2. **Signing identity and provenance.** Before any signed Beta candidate exists, define Owner-controlled key custody/recovery and the protected signing workflow under O-01/O-05. For an authorized candidate, bind source SHA → workflow run → APK SHA-256 → package/version → signer SHA-256; separately retain certificate SHA-1 only for any later Owner-approved OAuth binding. Verify the installed package signer against the packet read-only. A debug or CI temporary certificate cannot stand in for the Owner signer. No key creation, loading, or signing is part of this plan.
3. **Version and update lineage.** The inspected debug candidate uses code 1/name `0.1.0-demo`; a Beta candidate needs an explicitly selected `0.1.0` name and monotonic version code under Owner policy. Verify same-signer in-place forward update and preservation of synthetic encrypted history, settings, and schema. Exercise migration from each supported prior schema, interruption/restart recovery, and rejection of downgrade or signer mismatch. Recovery must use a correctly signed forward update or documented backup restore; never uninstall or clear app data to force an update.
4. **Backup, uninstall, and recovery.** Decide and verify backup policy for databases, preferences, credentials, and local model files. Prove sensitive data is excluded from unintended backup/cloud transfer, or document the Owner-approved encrypted backup and restore path. Use only a disposable package instance with synthetic fixtures to test uninstall/reinstall. Confirm uninstalling the candidate changes no sibling app state. Do not delete personal data, reset the Pixel, or use a personal profile for destructive test cases.
5. **Native ABI and library inventory.** Inspect the exact candidate APK's `lib/<abi>` entries, ELF machine/type, JNI registration, dependency closure, and load result. Require `arm64-v8a` for Pixel 7a. The #189 APK's AndroidX graphics library inventory does not prove Serea inference JNI. #195 has no hosted Android result in the inspected state and cannot establish ARM64. Keep native runtime `NOT_RUN` until a matching model/JNI build is loaded and exercised on the accepted ARM64 device or supported ARM64 runner. Report each ABI separately; x86_64/Rust matrix success does not imply Android ARM64 success.
6. **Crash and lifecycle recovery.** With synthetic conversations only, record cold launch, background/foreground, Activity recreation, OS process death, memory-pressure notification, local-model eviction/reload, cancellation during load/inference, and recovery after native/backend failure. Capture sanitized crash/ANR/exit-reason and tombstone summaries without message contents or identifiers. Verify consent/process-local state is not resurrected after process death, usage is settled or marked unknown consistently, and there is no automatic cloud or Demo fallback. Test only after a formally reviewed native composition is available; current #195 lifecycle tests are fake-provider evidence.
7. **Model placement and integrity.** O-10 remains undecided. No model is included in the #189 candidate. Before any local-model device test, independently approve model/revision/license and redistribution terms, publish required notices, and bind model SHA-256 to the packet. Place weights only in app-private internal storage, verify digest and expected size before JNI load, and prove update/eviction/reload behavior without shared external storage. Keep `LOCAL_MODEL_CHAT_ENABLED=false` in every product variant and do not connect the route to normal Chat until separate runtime, security, UX, and Owner gates pass.
8. **Network and account boundary.** G9 Fake Google tests use synthetic identities and fake providers. Device acceptance must use no real Google OAuth/account/data, no cloud API key or billing, and no unapproved network destination. Capture a sanitized network-boundary result showing local model requests do not trigger cloud/Demo fallback or transmit model prompts. Required identity behavior must remain unchanged.

## Non-destructive Pixel 7a sequence (Owner-authorized stage only)

This sequence is a proposed runbook. It is not permission to operate the device. Do not start it until O-06 is separately authorized and package/signing/version policy has been settled under O-01/O-05.

1. Confirm the named device/profile, OS/API, free storage, battery/thermal starting conditions, and that no personal data will be touched. If the profile may contain personal data or an existing Serea installation, stop before install.
2. Record package/version/signer and available storage read-only. Preserve the existing install. If coexistence is in scope, install only the authorized candidate into a disposable profile and verify both package IDs and app-private storage roots.
3. Populate synthetic history/settings and synthetic model fixtures only. Verify encrypted database open, expected schema, and backup exclusions before and after a same-signer forward update.
4. Run the lifecycle, cancellation, process-death, memory, crash/ANR, local ABI/model-integrity, offline/no-egress and thermal/performance cases. Record exact test IDs, sanitized outcome, resource measurements and recovery behavior.
5. Test a migration interruption and recovery only with a disposable synthetic profile and a preverified backup. Do not use uninstall/data clear as rollback. Verify signer mismatch and downgrade are rejected without altering existing data.
6. Verify uninstall/reinstall isolation only on the disposable candidate profile. Preserve any sibling Demo installation and its data. Recheck app data and package inventory afterward.
7. Store only sanitized reports, package/version/certificate fingerprints, artifact hashes, and synthetic-data results. Do not retain prompts, account data, tokens, private paths, or personal logs.
