### Why each enabled feature, and what is rejected

`bundled` is the only feature enabled, and it is doing two jobs:

- `libsqlite3-sys/bundled` — compiles SQLite **3.53.2** from the pinned source, so
  every developer and every CI machine gets the identical version and no system
  SQLite is involved. Verified: `otool -L` on the built binary lists **no
  `libsqlite3`**; the amalgamation is statically linked.
- `modern_sqlite` (implied by `bundled`) → `bundled_bindings` — `build.rs` copies
  the pre-generated `sqlite3/bindgen_bundled_version.rs`, so **no `bindgen` or
  `libclang` is needed** in CI.

`STRICT` tables need SQLite ≥ 3.37.0; generated columns need ≥ 3.31.0. We have
3.53.2. **Measured cost: 20 packages compiled** on `aarch64-apple-darwin`.

**Rejected, with the measured reason:**

| Feature | Why rejected | Measured cost of taking it |
| --- | --- | --- |
| rusqlite `default` = `["cache", "ffi-sqlite-wasm-rs"]` | pulls `hashlink`/`hashbrown`/`foldhash` for a prepared-statement cache P2 will not use, and `sqlite-wasm-rs` + `wasm-bindgen` + `js-sys` for a wasm VFS P2 will never run | 11 packages compiled with defaults — and, decisively, **no `cc`**, i.e. **no bundled SQLite**, i.e. *system* SQLite |
| `bundled-full` | `chrono`, `jiff`, `time`, `serde_json`, `url` (+ the whole `icu_*`/`idna` tree), `uuid`, `csv`, `series`, `vtab`, `window`, `load_extension`, `unlock_notify`, `column_metadata`, `trace`, `hooks`, `backup`, `collation`, `limits` | **81 packages compiled** vs 20 |
| `backup` | `sqlite3_backup_*` is for online backup of a *running* database. P2 moves a database by clean-stop → checkpoint → copy (§7.5 of the design) | — |
| `hooks` / `preupdate_hook` | `hooks` exposes `sqlite3_commit_hook`/`rollback_hook`. P2 does not need either: atomicity comes from the transaction, not from a callback that fires *after* the commit | — |
| `trace` | `sqlite3_trace_v2` is a statement profiler. No production need; it is a debugging aid | — |
| `limits` | exposes `sqlite3_hard_heap_limit64`/`soft_heap_limit64`. P2's bounds are Serea's (§5), not SQLite's, and `temp_store` is deliberately left at its default | — |
| `chrono` / `jiff` | SQLite returns times as text or as integers. Durable time is `INTEGER` epoch ms compared as integers; `Timestamp` is produced at the storage boundary from an injected `Clock`. Neither crate is needed, and both would drag a timezone database in | — |
| `load_extension` | **Rejected on principle, not because the engine lacks it.** The bundled amalgamation *is* compiled with `-DSQLITE_ENABLE_LOAD_EXTENSION=1`, so the C capability exists whether or not this Rust feature is on. Not enabling the Rust feature means Serea exposes no API for it. A claim that extension loading is "not compiled in" would be false; the accurate claim is that no Rust binding is linked | — |
| `unlock_notify` | a Windows/io_uring extension mechanism. P2 targets macOS and Linux | — |
| wasm-related defaults | `ffi-sqlite-wasm-rs` and `wasm32-wasi-vfs` exist only for `wasm32-unknown-unknown` / `wasm32-wasi`. P2's crates are host crates | — |

**One caveat that must not be recorded as a clean override.** `rusqlite` declares
its non-wasm `libsqlite3-sys` dependency **without** `default-features = false`, so
`libsqlite3-sys`'s own defaults — `min_sqlite_version_3_34_1` → `pkg-config` +
`vcpkg` — are **still enabled**, and those two build dependencies are still
compiled. What `bundled` overrides is the **discovery path**, not the compilation:
`build.rs` takes the bundled branch and never consults `pkg-config`. Verified by
link inspection, not assumed.

**A concrete reason `bundled` beats the system SQLite here, beyond consistency.**
SQLite's WAL documentation records the **WAL-reset bug** as present in all versions
"from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09)", fixed in **3.51.3
(2026-03-13)** and later. It can corrupt a WAL-mode database when two connections
write and checkpoint concurrently — which is Serea's shape, since a second
connection is used for lease tests and for recovery. Bundled **3.53.2** is past the
fix. This host's system SQLite is **3.43.2**, which is not, and the published
backports (`3.44.6`, `3.50.7`) do not cover it.

### `sha2` — verified

`0.11.0`, published 2026-03-25. `rust-version = "1.85"` — exactly the workspace
MSRV, and the only declared MSRV in the P2 dependency set. License **MIT OR
Apache-2.0**. `default-features = false` suffices: P2 computes a SHA-256 digest,
which needs neither `alloc` nor `oid`.

Two implementation facts P2B must not rediscover:

1. **`finalize()` returns `Array<u8, …>`, which does not implement `LowerHex`.**
   `format!("{:x}", h.finalize())` **does not compile** — measured. `0.10`'s
   `Output<Sha256>` did, so this is an API break across the version bump.
   Hex-encode explicitly and pin the result in the SCJ-1 vectors.
2. **Architecture behaviour is transparent.** `sha2` 0.11 takes an optional
   `cpufeatures` dependency on `aarch64`/`x86` and selects an `aarch64-sha2` or
   `x86-sha` hardware backend at **runtime**. The accelerated backends compute the
   same SHA-256, so digests are byte-identical across architectures. The
   acceleration is an implementation detail with no wire effect.

## 4. Migration-note drafts

Both are short **only** because `serea-core` and the Android client are P12 and no
task or action document has ever crossed a host boundary. That is true now and
stops being true at P12 — which is the argument for taking the major now rather
than calling it minor.

### 4.1 `serea.task/1` → `serea.task/2`

**Consumers that exist today** — the complete list, verified against the workspace:

| Consumer | Location | What must change |
| --- | --- | --- |
| Rust types | `crates/serea-protocol/src/types.rs` | `TaskStep`'s five fields become `Option`; `lease_generation` added as `Option<u32>`; construct via `StepPresence` |
| JSON Schema | `crates/serea-protocol/schemas/assistant-task.schema.json` | per-kind conditional `required`; `lease_generation` added |
| P1 tests | `crates/serea-protocol/tests/protocol_types.rs` (step fixture ~line 1292, round trips ~1321/1334, field lists ~201/1013), `tests/schema_contracts.rs` (~96, ~153–154, ~201, ~360), `tests/ids.rs` (`mod idempotency_key` ~224) | literals and field lists updated in the same commit |
| P1 fixtures | `fixtures/` — **empty; no fixture file exists** | nothing to migrate; the P2A test creates the first one |
| Internal host consumers | **none** — `serea-core` does not exist; the workspace is `serea-protocol` + `serea-testkit` only | — |
| Android task consumers | **none** — no `android/` tree exists | — |

**What changes:**

1. **Five `TaskStep` members become conditionally optional** — `capability_id`,
   `capability_version`, `provider_id`, `idempotency_key` (required only for
   `CAPABILITY`, `DELEGATE`, `VERIFY`) and `started_at`/`result_digest` per the
   ADR-0018 §3 presence matrix. Requiredness moves from unconditional to
   conditional; it is not simply dropped.
2. **`lease_generation` is introduced** as an optional field (ADR-0024).
3. **A `serea.task/1` consumer must not parse `serea.task/2` as `/1`.** The version
   tag is the discriminator; a `/1` consumer that ignored it would apply `/1`
   validation to a `/2` document. **No alias field and no dual-acceptance window** —
   the version tag is the whole mechanism.
4. **No fabricated timestamps or digests.** A planned step has no `started_at` and
   no `result_digest` because none exists. A sentinel — a zero timestamp, or
   `sha256:` of the empty string — is rejected: a durable audit record that lies,
   and a sentinel digest is indistinguishable from a real digest of an empty
   document.

**Persisted data migration: not required, and the precise reason.** P2 production
has never shipped. There is no P2 production database anywhere, no deployed
`serea-core`, and no Android client. The only durable artifacts that exist are P1's
source and tests. So this note is about **wire and source compatibility only** — no
row is rewritten, no stored document is converted, and no stored digest changes.

### 4.2 `serea.action/1` → `serea.action/2`

**Consumers that exist today:**

| Consumer | Location | What must change |
| --- | --- | --- |
| Rust types | `crates/serea-protocol/src/{types,provider,schema,ids,errors}.rs` | `ActionRequest`/`ActionResult` validation and the idempotency-key derivation call |
| JSON Schema | `crates/serea-protocol/schemas/action-request.schema.json`, `action-result.schema.json` | `message` widening per ADR-0023; category-O pattern regenerated |
| P1 tests | `crates/serea-protocol/tests/{protocol_types,schema_contracts,ids}.rs` | same commit |
| Internal host consumers | **none** — `serea-core` does not exist | — |
| Android action consumers | **none** — no `android/` tree exists | — |

**What changes:**

1. **IDK derivation changes to the explicit framed IDK-1 encoding.** Capability
   Protocol §8.2's `‖` becomes a byte layout: a 21-byte domain tag
   `serea.idempotency.v1\0`, a `u8` field count, then each of the five fields as
   `u64` big-endian length + bytes. Injective by construction rather than by
   accident of three grammars. Full layout and all vectors:
   [ADR-0019](../decisions/ADR-0019-canonical-json-and-idempotency-preimage.md).
2. **A `/1`-generated idempotency key is not reused as a `/2` key, and `/2` derives
   a fresh key under the `/2` rule.** This is not a formality. Under the naive `‖`
   reading, two different legal actions collide — `p.r.list` / `0.0.0` / `-12` and
   `p.r.list` / `0.0.0-1` / `2` both produce the same 16 trailing bytes. IDK-1
   separates them, so **every key changes** and no stored key survives the bump.
3. **Text-validation domain changes covered by ADR-0023 are part of the new
   contract.** Three categories, one validator each, with the category-O rule being
   variant **C**. ADR-0023's measured basis: A catches 11/16 impersonations with
   0/14 false positives, B catches 15/16 with **8/14** false positives (refusing
   `calendar`, `worker`, `worker-1`, `host-a3f9` — every plausible `LeaseOwner`),
   and **C catches 16/16 with 0/14**. Do not re-derive this; the excluded domains
   are stated in ADR-0023. The generated schema pattern must additionally subtract
   the `goallatch` namespace, because `CapabilityId` refuses `goallatch` as a
   provider — a pattern merely *stricter* than `CapabilityId` is still a parity bug.
4. **SCJ-1 behaviour is pinned by fixed vectors.** Ten canonical-bytes vectors and
   ten digests, plus seven IDK-1 keys. **All were re-derived independently during
   this closure run and all 34 checks reproduce**, including the 282-byte preimage
   for vector 1 and the vector-8 provenance.

**Persisted data migration: not required, for the same precise reason** — no P2
production database exists, so there is no stored `idempotency_key` to re-derive and
no stored `arguments_digest` to recompute. The statement is about the *current*
state of the world, not a promise about P12.

## 6. Moving a database to the other Mac

**Normal path — the procedure to put in user-facing documentation:**

1. **Stop Serea** (the process, so the last connection closes cleanly).
2. **Confirm no other reader or writer** holds the file — a second Serea instance,
   a `sqlite3` shell, a backup agent.
3. **Checkpoint:** `PRAGMA wal_checkpoint(TRUNCATE)`. **Check the `busy` column** —
   it returns `1` and completes only partially while another connection holds a
   read snapshot, so `busy = 1` means *stop and find that connection*.
4. **Close all connections.** This deletes `-wal` and `-shm`, which is the point.
5. **Copy `serea.sqlite` alone.**
6. **Open it on the destination** — normal open checks run automatically.
7. **Run the migration, integrity and recovery checks** before trusting the data.

**Abnormal case — Serea did not stop cleanly and committed frames remain in the
`-wal`:** confirm nothing holds the source file (**never** copy a `-wal` from a live
writer — the copy is not atomic against SQLite's appends), then copy
`serea.sqlite` **and `serea.sqlite-wal`**, **still not the `-shm`**. On open,
SQLite rebuilds the wal-index and recovers the committed frames.

| File | Status | Carry it? |
| --- | --- | --- |
| `serea.sqlite` | durable asset; big-endian, cross-platform | **yes, always** |
| `serea.sqlite-wal` | durable asset **when committed frames are uncheckpointed**; big-endian, cross-platform | **yes, if it exists** |
| `serea.sqlite-shm` | **transient artifact**; native byte order, architecture-specific by upstream's own statement | **no, never** |

Upstream, verbatim: *"Because the wal-index is transient, it can use an
architecture-specific format; it does not have to be cross-platform. Hence, unlike
the database and WAL file formats which store all values as big endian, the
wal-index stores multi-byte values in the native byte order of the host
computer."* Full treatment: [design §7.5](P2-storage-task-engine.md#75-moving-a-serea-database-to-another-machine).

### 8.3 The atomicity requirement

**One commit. Not splittable.** A `serea.task/2` schema beside `serea.task/1` Rust
types is a state no other phase should observe, and the intermediate commits do not
build — `serde(try_from = Draft)` makes the Rust side permissive while the schema
is strict, so a `PLANNED` step would round-trip in Rust and be rejected by the
frozen schema.

Enforce it with **one parity test**: every cell in the Rust `StepPresence` matrix
has a schema counterpart and every schema cell has a Rust counterpart. That test is
what makes "atomic" checkable rather than aspirational, and it is the only thing
that catches one surface updated and the other missed.

### 8.4 Forbidden scope for P2A

- No `serea-storage` or `serea-task-engine` runtime.
- No migration file used by production.
- No `rusqlite`/`sha2` wiring beyond the dependency line — that is P2C/P2B.
- No `Cargo.lock` change beyond what the added dependency requires.
- No CI change.
- No ADR moved to `Accepted`.
- No architecture or wire version changed anywhere **except** the four surfaces in
  §2, in this commit.
- No `serea-event-bus`, no `E3`/`E4` claim, no GoalLatch or Local MCP integration.
- No P3 work.

## 9. P2A recommended implementation order

**Option C — tests for both surfaces first, then Rust + schema together, then
protocol/version/changelog/migration notes.** Full comparison of A, B and C with the
reasoning: [design §15.0](P2-storage-task-engine.md#150-ordering-inside-the-single-atomic-p2a-commit).

| Step | Action | Gate |
| --- | --- | --- |
| 1 | Rust matrix test, one `PLANNED` cell | **RED** on the type shape |
| 2 | Schema test, same cell | **RED** on the missing `if`/`then` |
| 3 | `StepPresence`, five `Option` fields, `serde(try_from = Draft)` | 1 GREEN |
| 4 | Schema conditional `required`, incl. the category-O pattern and `goallatch` subtraction | 2 GREEN |
| 5 | `lease_generation` optional, both surfaces | both GREEN |
| 6 | ADR-0023's three text categories, both surfaces | both GREEN |
| 7 | **Parity check** — Rust matrix ↔ schema, both directions | passes |
| 8 | `serea-arch/0.2.0 → 1.0.0`; `serea.task/1 → 2`; `serea.action/1 → 2` | — |
| 9 | Changelog entry per affected protocol document | §7 items 2, 3 |
| 10 | Both migration notes | §7 item 4 |
| 11 | Whole workspace green; **one** commit | §8.5 |

**Why not A** (Rust first): the Rust side goes green while the *authoritative* wire
artifact is still wrong, and `try_from = Draft` makes it pass anyway — a green build
over a broken contract. **Why not B** (schema first): the RED becomes a runtime
schema-validation failure in P1's existing tests rather than a compile error, so the
signal is real but the diagnosis points at data instead of at a type-contract
change.

**Step 7 is the one that is easy to skip and the one that matters most.**
