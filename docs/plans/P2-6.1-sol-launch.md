## 3. Dependency lines — current P2A integration and P2C candidate

**Current P2A wiring**, present in the coordinator's integration tree:

```toml
# workspace [workspace.dependencies]
serde_json = "=1.0.151"
sha2 = { version = "0.11.0", default-features = false }
jsonschema = { version = "=0.58.3", default-features = false }

# workspace [patch.crates-io]
jsonschema-value = { path = "vendor/jsonschema-value" }
serde_json = { path = "vendor/serde_json" }

# crates/serea-protocol/Cargo.toml [dependencies]
serde_json = { workspace = true, features = ["raw_value"] }
jsonschema = { workspace = true, features = ["arbitrary-precision"] }
```

`serde_json/raw_value` preserves the field-local generation token. Exact decimal/
exponent analysis accepts mathematically integral values in `1..=u32::MAX`
without an f64 conversion, so `1.0`/`1e0` accept while a near-integer fraction,
zero or overflow refuses. This is wire admission, not SCJ-1 admission: canonical
hashing still refuses decimal/exponent spellings. `jsonschema/arbitrary-precision`
also enables serde_json's `arbitrary_precision`, preserving numeric text in Value
inputs and direct schema validation.

The exact `jsonschema =0.58.3` pin accompanies a narrow offline path patch to its
`jsonschema-value` dependency. The workspace excludes the vendor crate from its
members. The patch removes rounded-f64 fallback from precision-enabled integer
classification, checks decimal-shift subtraction/conversion, avoids signed-minimum
negation overflow and checks the actual denominator power against the existing
cap. It supports exact integer classification and safe conversion for the
existing bounded wire integers, **not unrestricted exact schema arithmetic**:
upstream equality, bounds and `multipleOf` still have f64 fallbacks/conversion
caps. It adds no general numeric resource budget and establishes no guarantee
for arbitrary fractional schemas, `const`/`enum`/`uniqueItems` or large numeric
bounds. Provenance, license, regression commands and removal conditions are in
`vendor/jsonschema-value/README.vendor.md`; actual run results belong in the
[closure record](P2A-review-and-closure.md). Network/file resolution remains
disabled by `default-features = false`; no SQLite or async runtime is introduced.

The companion `serde_json =1.0.151` pin and `vendor/serde_json` path patch
preserve literal objects whose keys match private Number/RawValue tokens.
Internal synthetic keys carry a Serde newtype discriminator; ordinary JSON string
keys stay ordinary even through Value replay and derive-flatten Content buffers.
Genuine nonnative numbers replay through exact synthetic maps, not rounded f64 or
eager wide-integer events that flatten cannot buffer. Explicit numeric targets
remain unchanged. Ten tests in `json_value_preservation.rs` cover raw/slice/reader,
owned/borrowed Value, action/schema verdicts, Trace/two-layer flatten and genuine
Number/RawValue transport. No legal keys are banned, and both precision features
remain enabled. Provenance, private-transport compatibility limits and removal
criteria are in `vendor/serde_json/README.vendor.md`. Both vendor crates are excluded
from workspace membership; unchanged optional adapters are not Serea runtime.

### Why each enabled feature, and what is rejected

For the P2C candidate's historical probe, `bundled` is the only selected rusqlite
feature, doing two jobs:

- `libsqlite3-sys/bundled` — compiles SQLite **3.53.2** from the pinned source, so
  every developer and every CI machine gets the identical version and no system
  SQLite is involved. Verified: `otool -L` on the built binary lists **no
  `libsqlite3`**; the amalgamation is statically linked.
- `modern_sqlite` (implied by `bundled`) → `bundled_bindings` — `build.rs` copies
  the pre-generated `sqlite3/bindgen_bundled_version.rs`, so **no `bindgen` or
  `libclang` is needed** in CI.

`STRICT` tables need SQLite ≥ 3.37.0; generated columns need ≥ 3.31.0. We have
3.53.2. **Measured cost: 20 packages compiled** on `aarch64-apple-darwin`.

**Rejected, with the measured reason:**

| Feature | Why rejected | Measured cost of taking it |
| --- | --- | --- |
| rusqlite `default` = `["cache", "ffi-sqlite-wasm-rs"]` | pulls `hashlink`/`hashbrown`/`foldhash` for a prepared-statement cache P2 will not use, and `sqlite-wasm-rs` + `wasm-bindgen` + `js-sys` for a wasm VFS P2 will never run | 11 packages compiled with defaults — and, decisively, **no `cc`**, i.e. **no bundled SQLite**, i.e. *system* SQLite |
| `bundled-full` | `chrono`, `jiff`, `time`, `serde_json`, `url` (+ the whole `icu_*`/`idna` tree), `uuid`, `csv`, `series`, `vtab`, `window`, `load_extension`, `unlock_notify`, `column_metadata`, `trace`, `hooks`, `backup`, `collation`, `limits` | **81 packages compiled** vs 20 |
| `backup` | `sqlite3_backup_*` is for online backup of a *running* database. P2 moves a database by clean-stop → checkpoint → copy (§7.5 of the design) | — |
| `hooks` / `preupdate_hook` | `hooks` exposes `sqlite3_commit_hook`/`rollback_hook`. P2 does not need either: atomicity comes from the transaction, not from a callback that fires *after* the commit | — |
| `trace` | `sqlite3_trace_v2` is a statement profiler. No production need; it is a debugging aid | — |
| `limits` | exposes `sqlite3_hard_heap_limit64`/`soft_heap_limit64`. P2's bounds are Serea's (§5), not SQLite's, and `temp_store` is deliberately left at its default | — |
| `chrono` / `jiff` | SQLite returns times as text or as integers. Durable time is signed `INTEGER` epoch ms using the distinct bounded `EpochMillis`, compared numerically; the injected Clock returns EpochMillis, not unsigned48 ULID TimestampMs. Shared protocol Timestamp conversion produces canonical `.mmmZ` at later storage boundaries and in TestClock; no second parser/calendar is needed. Neither crate is needed, and both would drag a timezone database in | — |
| `load_extension` | **Rejected on principle, not because the engine lacks it.** The bundled amalgamation *is* compiled with `-DSQLITE_ENABLE_LOAD_EXTENSION=1`, so the C capability exists whether or not this Rust feature is on. Not enabling the Rust feature means Serea exposes no API for it. A claim that extension loading is "not compiled in" would be false; the accurate claim is that no Rust binding is linked | — |
| `unlock_notify` | a Windows/io_uring extension mechanism. P2 targets macOS and Linux | — |
| wasm-related defaults | `ffi-sqlite-wasm-rs` and `wasm32-wasi-vfs` exist only for `wasm32-unknown-unknown` / `wasm32-wasi`. P2's crates are host crates | — |

**One caveat that must not be recorded as a clean override.** `rusqlite` declares
its non-wasm `libsqlite3-sys` dependency **without** `default-features = false`, so
`libsqlite3-sys`'s own defaults — `min_sqlite_version_3_34_1` → `pkg-config` +
`vcpkg` — are **still enabled**, and those two build dependencies are still
compiled. What `bundled` overrides is the **discovery path**, not the compilation:
`build.rs` takes the bundled branch and never consults `pkg-config`. Verified by
link inspection, not assumed.

**A concrete reason `bundled` beats the system SQLite here, beyond consistency.**
SQLite's WAL documentation records the **WAL-reset bug** as present in all versions
"from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09)", fixed in **3.51.3
(2026-03-13)** and later. It can corrupt a WAL-mode database when two connections
write and checkpoint concurrently — which is Serea's shape, since a second
connection is used for lease tests and for recovery. Bundled **3.53.2** is past the
fix. This host's system SQLite is **3.43.2**, which is not, and the published
backports (`3.44.6`, `3.50.7`) do not cover it.

### `sha2` — verified

`0.11.0`, published 2026-03-25. `rust-version = "1.85"` — exactly the workspace
MSRV, and the only declared MSRV in the P2 dependency set. License **MIT OR
Apache-2.0**. `default-features = false` suffices: P2 computes a SHA-256 digest,
which needs neither `alloc` nor `oid`.

Two implementation facts P2A must not rediscover:

1. **`finalize()` returns `Array<u8, …>`, which does not implement `LowerHex`.**
   `format!("{:x}", h.finalize())` **does not compile** — measured. `0.10`'s
   `Output<Sha256>` did, so this is an API break across the version bump.
   Hex-encode explicitly and pin the result in the SCJ-1 vectors.
2. **Architecture behaviour is transparent.** `sha2` 0.11 takes an optional
   `cpufeatures` dependency on `aarch64`/`x86` and selects an `aarch64-sha2` or
   `x86-sha` hardware backend at **runtime**. The accelerated backends compute the
   same SHA-256, so digests are byte-identical across architectures. The
   acceleration is an implementation detail with no wire effect.

| Android task consumers | **none** — no `android/` tree exists | — |

**What changes:**

1. **Four members become Option**: `idempotency_key`, `result_digest`,
   `started_at`, `completed_at`. `input_digest` stays required;
   provider/capability/version already are Option. Exactly seven fields are
   unconditional. Known statuses enforce presence; kind invariants always apply.
   Unknown well-formed wire status parses, with execution blocking deferred.
   Missing/null both mean None and serialization omits None. SQL generation 0
   maps to None; positive u32 generations survive release; overflow is refused
   (SQL mapping/runtime remains deferred). All five non-capability kinds must
   omit receipts on ALL statuses, including unknown codes; they cannot carry
   external action semantics.
2. **`lease_generation` is introduced** as an optional validated wire field
   (ADR-0024). This implements no acquisition/revocation/fencing runtime.
   Construct drafts and validate before use; checked `TaskStep`/`StepPresence`
   state is private. Unknown extensions round-trip, but any extension key equal
   to a reserved step member is refused, even if the member is absent. To update
   a checked step, convert it to a draft and revalidate. The Rust field remains
   `Option<u32>`; generation wire decoding accepts integer-valued JSON numeric
   spellings such as `1.0` and `1e0`, with exact positive-u32 validation using
   field-local RawValue tokens, not f64 rounding. Precision-enabled Value inputs
   and direct schema validation preserve numeric text. Missing/null remain None;
   zero, true fractions (including near-integers) and overflow refuse. This is not SCJ-1 numeric
   admission: canonical hashing still refuses decimal/exponent spellings.
   `TaskStep` uses manual `Deserialize`: decode a draft, sanitize draft failures
   to `invalid task step draft` without formatting the rejected error, then call
   `StepPresence::new`. It does not use `serde(try_from = ...)` for deserialization;
   unchecked draft errors are not independently claimed sanitized.
3. **A `serea.task/1` consumer must not parse `serea.task/2` as `/1`.** The version
   tag is the discriminator; a `/1` consumer that ignored it would apply `/1`
   validation to a `/2` document. **No alias field and no dual-acceptance window** —
   the version tag is the whole mechanism.
4. **No fabricated timestamps or digests.** A planned step has no `started_at` and
   no `result_digest` because none exists. A sentinel — a zero timestamp, or
   `sha256:` of the empty string — is rejected: a durable audit record that lies,
   and a sentinel digest is indistinguishable from a real digest of an empty
   document.

**Persisted data migration: not required, and the precise reason.** P2 production
has never shipped. There is no P2 production database anywhere, no deployed
`serea-core`, and no Android client. The only durable artifacts that exist are P1's
source and tests. So this note is about **wire and source compatibility only** — no
row is rewritten, no stored document is converted, and no stored digest changes.

   Protocol §8.2's `‖` becomes a byte layout: a 21-byte domain tag

4. **SCJ-1 behaviour is pinned by fixed vectors.** Ten canonical-bytes vectors and

## 6. Moving a database to the other Mac

**Normal path — the procedure to put in user-facing documentation:**

1. **Stop Serea** (the process, so the last connection closes cleanly).
2. **Confirm no other reader or writer** holds the file — a second Serea instance,
   a `sqlite3` shell, a backup agent.
3. **Checkpoint:** `PRAGMA wal_checkpoint(TRUNCATE)`. **Check the `busy` column** —
   it returns `1` and completes only partially while another connection holds a
   read snapshot, so `busy = 1` means *stop and find that connection*.
4. **Close all connections.** This deletes `-wal` and `-shm`, which is the point.
5. **Copy `serea.sqlite` alone.**
6. **Open it on the destination** — normal open checks run automatically.
7. **Run the migration, integrity and recovery checks** before trusting the data.

**Abnormal case — Serea did not stop cleanly and committed frames remain in the
`-wal`:** confirm nothing holds the source file (**never** copy a `-wal` from a live
writer — the copy is not atomic against SQLite's appends), then copy
`serea.sqlite` **and `serea.sqlite-wal`**, **still not the `-shm`**. On open,
SQLite rebuilds the wal-index and recovers the committed frames.

| File | Status | Carry it? |
| --- | --- | --- |
| `serea.sqlite` | durable asset; big-endian, cross-platform | **yes, always** |
| `serea.sqlite-wal` | durable asset **when committed frames are uncheckpointed**; big-endian, cross-platform | **yes, if it exists** |
| `serea.sqlite-shm` | **transient artifact**; native byte order, architecture-specific by upstream's own statement | **no, never** |

architecture-specific format; it does not have to be cross-platform. Hence, unlike
the database and WAL file formats which store all values as big endian, the
wal-index stores multi-byte values in the native byte order of the host
computer."* Full treatment: [design §7.5](P2-storage-task-engine.md#75-moving-a-serea-database-to-another-machine).

### 8.3 The atomicity requirement

**One P2A commit. Not splittable; no preliminary docs commit.** A `serea.task/2`
schema beside `serea.task/1` Rust types is a state no other phase should observe.
The implemented `TaskStepDraft` → checked `TaskStep`/`StepPresence` boundary is
validated, not permissive: Rust and schema must change together so a planned
step cannot pass only one side.

Enforce it with **one parity test**: every cell in the Rust `StepPresence` matrix
has a schema counterpart and every schema cell has a Rust counterpart. That test is
what makes "atomic" checkable rather than aspirational, and it is the only thing
that catches one surface updated and the other missed.

- No `Cargo.lock` change beyond the P2A hash/precision dependencies and narrow vendor patch.

- No P3 work.

### 8.6 What P2B may start only after P2A closes

**P2B only — frozen accepted corrected design.** All P2B BLOCKER/MAJOR design
findings are accepted and resolved by this design before production. This is not
an implementation/test PASS or a P2B completion claim. SCJ-1, digest and IDK-1 are
already required at the P2A gate.

- Introduce distinct `EpochMillis` with a **private `i64` field**, checked
  constructor, `get()` and numeric `Ord`. Inclusive bounds:
  `MIN = -62_167_219_200_000` (`0000-01-01T00:00:00.000Z`),
  `MAX = 253_402_300_799_999` (`9999-12-31T23:59:59.999Z`). The existing
  `TimestampMs` remains unchanged unsigned48 ULID time, not the full signed
  wire-domain or Clock type.
- Keep Timestamp grammar exactly seconds or `.mmmZ`, with year0000 legal.
  Existing Timestamp objects retain exact wire spelling and spelling-based
  serialization/`Eq`/`Hash`. To epoch preserves the instant; from epoch always
  emits canonical `.mmmZ` (including `.000Z`), **not original-spelling recovery**.
  Remove Timestamp `PartialOrd`/`Ord`; no repository consumers need migration.
- Add `Clock: Send + Sync` with synchronous object-safe
  `fn now_ms(&self) -> Result<EpochMillis, ProtocolError>`. Injection only;
  no async runtime or ambient/system clock implementation.
- Make TestClock `start_ms`/`now_ms` EpochMillis; elapsed is their difference.
  Reuse Timestamp validation/conversion for `at` and canonical `format`, accept
  seconds input/year0000/negative epochs, and retain no private calendar/parser.
  Checked atomic `advance` validates duration magnitude before narrowing,
  addition and domain bounds; even `Duration::MAX` returns a typed error without
  mutating current/elapsed time. Zero/exact-MAX advance remains valid.
- Require corrected E1–E7 plus API/ULID regressions: bounds and construction
  refusal, wire/calendar and leap boundaries, instant round-trip/canonical output,
  exact spelling/Eq/Hash, explicit **string** ordering versus equal/chronological
  epoch ordering, removal of Timestamp ordering, deterministic dyn Clock and
  atomic TestClock overflow. E7 checks **current protocol/testkit P2B sources and
  tests**, embedded examples and any build scripts present, not new crates.
  Store-open clock-error behavior is **P2C**; successful EpochMillis readings
  already satisfy bounds by construction.

Full implementation scope and evidence obligations:
[design §8](P2-storage-task-engine.md#8-clock-and-time-representation),
[§15.2](P2-storage-task-engine.md#152-p2b-clock-and-time-only), and
[Group E](P2-test-matrix.md#7-group-e-clock-and-time). No storage implementation,
new storage/engine crate, ADR, schema or protocol-version change belongs to this
P2B correction. Historical P2A evidence remains unchanged.

**Not** P2C. `serea-storage` may not begin until the presence and classification
rules P2A fixes are the ones it persists — building a durable store on a wire
contract that cannot represent a planned step is the failure this phasing exists to
prevent.
