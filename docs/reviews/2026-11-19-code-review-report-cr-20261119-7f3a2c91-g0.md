## Major

### F1 Major - Isolated Live composition accepts a production Google endpoint

Impact: `The test-only Live path can construct a bearer-capable client with the production Google Calendar base URL, contrary to the no-external-HTTP boundary.`
Review reason: `The isolated build-type guard does not constrain destination; omitting baseUrl selects the existing production endpoint, and the production URL also passes the transport allowlist.`
Surface: `PrivateGoogleCalendarComposition -> CalendarProviderSessions.openPrimaryGoogleReadOnly -> GoogleCalendarHttpReadPort.`
Issue key: `behavior; entry=isolated primary provider composition; contract=all test HTTP targets loopback MockWebServer; effect=missing or external endpoint permits Google request`
Issue fingerprint: `ifp-sha256:ad5b065a852e4b61696c075175225677fa73fc4223a7e1ed5707d1254748b582`
Expected basis: `kind:approved-design; strength:authoritative; evidence:docs/superpowers/plans/2026-11-18-private-google-calendar-live-provider.md Task 3 and Global Constraints require MockWebServer loopback only`
Confidence: `high`
Origin: `R1-endpoint; Coordinator`
Coordinator verification: `Confirmed constructor only checks BUILD_TYPE; null is forwarded to CalendarProviderSessions, which omits an explicit URL and therefore uses GoogleCalendarHttpReadPort.GOOGLE_API_BASE. The HTTP transport explicitly permits that production host.`

Look here first:
- [PrivateGoogleCalendarComposition.kt](../../android/app/src/main/java/app/serea/android/googleauth/PrivateGoogleCalendarComposition.kt#L15-L55)
- [CalendarProviderSessions.kt](../../android/app/src/main/java/app/serea/android/calendar/CalendarProviderSessions.kt#L71-L99)

Failure mode:
- Expected: `Every explicitly selected test Live composition must require a concrete loopback MockWebServer URL before authorization status or token access.`
- Current: `An isolated Live composition accepts null or https://www.googleapis.com/calendar/v3/; the existing lower-level transport treats null as its production Google endpoint.`

Evidence:
- `PrivateGoogleCalendarComposition.kt:15-23 checks only that the build type is isolated; baseUrl defaults to null.`
- `PrivateGoogleCalendarComposition.kt:53-55 forwards null to openPrimaryGoogleReadOnly.`
- `CalendarProviderSessions.kt:86-98 omits the base URL when null; GoogleCalendarHttpReadPort.kt:68,83-89 defaults to and allows https://www.googleapis.com/calendar/v3/.`
- `No external request was made during review; the defect is in allowed endpoint construction, not an observed real network call.`

Assumptions and limits:
- `A caller must also choose Live and invoke a read. Product variants remain protected by the separate isolated-build check. The synthetic test gateway currently uses an invalid-for-Google token, but the endpoint policy must not depend on token validity.`

Reviewer action:
`Require and validate a loopback URL in the isolated Live composition and add rejection tests for null and production URLs.`

### F2 Major - Provider may bind to a replacement authorization session

Impact: `The agenda may be bound to a different authorization session/account than the session whose status was checked.`
Review reason: `The final pre-construction identity comparison is not bound into adapter construction; a concurrent session change in that interval can let the adapter capture the replacement identity.`
Surface: `PrivateGoogleCalendarComposition.openAuthorizedPrimary -> CalendarProviderSessions.openPrimaryGoogleReadOnly -> GoogleCalendarAuthorizationAdapter constructor.`
Issue key: `behavior; entry=authorized Primary session construction; contract=provider token adapter stays bound to the session that passed authorization; effect=replacement session can authorize a read after account switch`
Issue fingerprint: `ifp-sha256:a57e6a400a177f6dbe29f914c1283f961ae18d6e9f1d4a4a675d9be4c220bee2`
Expected basis: `kind:owner-decision; strength:authoritative; evidence:Owner conditions 5-6 and approved design require the current authorization session and fail-closed account-switch behavior`
Confidence: `medium`
Origin: `R1-session; Coordinator`
Coordinator verification: `Confirmed that composition captures and checks sessionId before construction, while GoogleCalendarAuthorizationAdapter independently captures gateway.authorizationSessionId during construction. No expected-session value is passed across that boundary.`

Look here first:
- [PrivateGoogleCalendarComposition.kt](../../android/app/src/main/java/app/serea/android/googleauth/PrivateGoogleCalendarComposition.kt#L32-L55)
- [GoogleCalendarAuthorizationAdapter.kt](../../android/app/src/main/java/app/serea/android/googleauth/GoogleCalendarAuthorizationAdapter.kt#L16-L21)

Failure mode:
- Expected: `The Provider adapter must remain bound to the exact authorization session that passed status validation; if identity changes before construction completes, construction must fail before token or HTTP use.`
- Current: `A gateway can report session A for both composition checks, switch to B before adapter construction, and have the adapter capture B. Its later token checks then validate B rather than the previously validated A.`

Evidence:
- `Composition checks gateway.authorizationSessionId before and after status at PrivateGoogleCalendarComposition.kt:33-51, then calls the session factory at lines 53-55.`
- `CalendarProviderSessions.kt:86 constructs GoogleCalendarAuthorizationAdapter; its line 20 captures the current gateway session ID.`
- `Existing tests cover changes during status and after session construction, but not this construction handoff window (PrivateGoogleCalendarCompositionTest.kt:149-179).`

Assumptions and limits:
- `The gateway session identity may change concurrently; no real-account race was reproduced. A deterministic synthetic gateway can change identity on the adapter-capture read and prove the boundary without external access.`

Reviewer action:
`Add an expected-session handoff check and a deterministic construction-window regression test; close any session created under the replacement identity.`
