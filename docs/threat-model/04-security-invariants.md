# Serea Threat Model: Security Invariants

Part of `serea-tm/0.1.0` · Written against `serea-arch/0.1.0` and the P0-frozen protocols.

Index: [Threat model index](README.md) · Previous: [03 — Abuse cases and mitigations](03-abuse-cases-and-mitigations.md)

This document is the normative cross-reference between threat-model security claims, frozen protocol guarantees, the abuse cases that depend on them, and verification obligations. `INV-SEC-*` identifiers are local to this threat model; they do **not** add protocol types or change protocol semantics. The protocols remain authoritative. A frozen contract is not evidence that implementation exists or passed a test.

## 1. Reading the table

- **Source protocol invariants** are exact IDs from the frozen protocol summary tables. A cited ID supports only the guarantee stated by its protocol; it must not be stretched to imply a missing control.
- **Dependent abuse cases** link to the corresponding cards in [03](03-abuse-cases-and-mitigations.md#3-abuse-case-cards).
- **Verification** references `SEC-CHK-nn` in §5 and names the architecture phase band. Phase bands locate implementation responsibility; phase plans own exact plan test IDs and release evidence.
- Where a required control has no protocol basis, it is recorded in §6 as aspirational/unimplemented rather than assigned a fictional source invariant.

## 3. Invariant prefixes

The source prefix mapping is normative and identical to [03 §2](03-abuse-cases-and-mitigations.md#2-invariant-prefixes): `C` Capability, `T` Task, `M` Model, `P` Policy, `A` Approval, `E` Event, `D` Device, `G` GoalLatch Adapter, `DC` Data Classification, `B` Bounds. Full source documents and their summary anchors are linked in that section. A bare prefix plus number is never a threat-model invariant; `INV-SEC-*` labels are reserved for this package.

## 4. Functional versus security invariants

Security and functional correctness overlap but are not interchangeable. The table identifies the primary purpose of each normative threat-model invariant; an invariant may still support both properties.

| Threat-model invariants | Primary classification | Reason |
| --- | --- | --- |
| `INV-SEC-01`–`INV-SEC-03`, `INV-SEC-05`–`INV-SEC-10`, `INV-SEC-15`–`INV-SEC-20` | **Security** | Preserve authority boundaries, confidentiality, approval scope, trusted provenance, and fail-closed behavior against adversarial inputs. |
| `INV-SEC-04`, `INV-SEC-11`, `INV-SEC-12`, `INV-SEC-14` | **Both** | Receipts, state isolation, reconciliation, and audit accuracy prevent harmful effects while also providing crash correctness and truthful status. |
| `INV-SEC-13`, `INV-SEC-21` | **Both** | Bounds protect availability/cost and limit the quantity of authorized or adversarial work; they do not themselves grant or deny authority. |

A useful separation: a functional invariant can be met during honest operation yet fail against a malicious actor; a security invariant constrains an adversarial path. Passing a functional happy-path test alone is not proof of the security property.

| External model vendor quota is bounded independently of Serea's local token/spend estimates. | **No dedicated provider quota bound.** `B14` bounds local accounting behavior; a changed price/quota may exceed estimates. | [AB-25](03-abuse-cases-and-mitigations.md#ab-25-cost-exhaustion-and-provider-quota-burn), `SEC-CHK-23`. Do not implement real integration as part of this documentation task. |

## 7. Change and evidence discipline

1. If implementation fails a frozen protocol invariant, fix implementation or treat it as a protocol violation; do not weaken this mapping to make a test green.
2. If a desired property has no source invariant, retain it in §6 and follow [Protocol Index §7 change control](../protocols/00-protocol-index.md#7-change-control) before claiming it as a guarantee.
3. A `SEC-CHK` passing in a mock-only unit test proves only that test's host logic. Provider, Android, durable-storage, and future GoalLatch claims require their corresponding integration artifacts in §5.
4. A phase label is not completion evidence. Completion requires the mapped executable test, its result, and any named live artifact; missing evidence remains unverified.
