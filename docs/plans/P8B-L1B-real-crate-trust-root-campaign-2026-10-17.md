## Observed crate ownership and attack surface

### W — Worker / Lease

`serea-storage::Tx::acquire_lease` is public and accepts a caller-created `LeaseOwner`, timestamps, task/step IDs and expected generation. An external consumer can therefore create durable lease state without any Host admission. `LeaseGuard` itself is non-Clone, has private fields, redacted Debug, and carries task, step, owner, generation and a private Store-origin marker. `Tx::observe_lease_facts` uses private `matching()` and proves that the same live Store origin and durable unreleased row match. This is durable-row/guard integrity, not Worker identity or Host incarnation.

The current dependency direction is Host → TaskEngine → Policy → Storage (and Host also directly depends on Storage under `synthetic`). `pub(crate)` cannot bridge these crate boundaries. A Host-private issuer wrapped around today's public Storage acquisition does not close the bypass. Before any adoption, Owner must choose whether the Worker admission boundary belongs in a new narrowly scoped authority crate or in Host with Storage's raw public acquisition removed/restricted and all lease operations routed through the approved Host boundary. A shared crate with a public mint function is not private authority: any downstream Cargo consumer can call it. B requires an actual authenticated IPC/session verifier and cannot be claimed from an in-process token.

### T — time

`Store::transact` creates a SQLite `TransactionBehavior::Immediate` transaction before invoking its closure. This gives a useful test seam: a locally injected `Clock` sampled as the first operation in the closure is sampled after the write reservation succeeds. Existing lease/approval APIs still take caller-supplied `EpochMillis`; no runtime authorization check uses a Host-owned clock. `now == expires_at` is expired in existing lease renewal and approval request logic, but that endpoint alone does not authenticate the supplied time.

T-A avoids stale pre-lock samples when the synchronous clock read is bounded and local. It cannot establish OS clock authenticity. T-B has a measurable stale-window risk equal to lock wait and requires a freshness bound/retry policy. Rollback, forward jumps, suspend, and restart need an Owner policy; a process-local high-water mark cannot survive restart, and a durable high-water mark is not tamper proof against a local database attacker.

### G — full Grant membership

Migration `0005` bounds membership positions to 0..7, makes `(grant_id, position)` primary and `(grant_id, step_id)` unique, checks every member against an approved request action and task, and fences update/delete. Migration `0006` requires count=`action_count`, max position=`action_count-1`, a seal row before use, and no insert after seal. The typed response writer inserts the complete selected subset and seal within its transaction. `action_set_digest` is computed over the request's ordered action set; the Grant can contain a selected subset, so this digest is not a digest of the granted subset. `approval_grant_seals` stores `sealed_at_ms`, not a cryptographic hash or versioned commitment. The effective protection is SQLite constraints/triggers plus typed writer fencing, not tamper evidence against a file/DDL attacker.

`observe_grant_facts` returns selected-Step digests, count, seal presence, status and use facts but does not enumerate the complete member set. `verify_integrity` checks SQLite page/FK and selected application histories, not the cryptographic authenticity of a local SQLite file. Existing SQL corruption tests demonstrate trigger defense and direct corruption behavior, but no production reader recomputes the full set and validates all members in one observation. G-A is therefore not established. A read-only G-B must enumerate deterministic `position` order under the same `BEGIN IMMEDIATE`, reject count/position/uniqueness/request-action mismatch and compare every row to the request and selected Step facts; the protocol ceiling is eight, but Owner must approve using it as the permanent probe contract.

### O — Owner verifier

`ApprovalResponseCandidateV1::new` is public and caller input. `AuthenticatedApprovalResponseV1::authenticate` is also public and accepts a verifier implementation supplied by the caller. The external positive probe implements a verifier that always returns `Ok(())` and successfully compiles the minting of `AuthenticatedApprovalResponseV1`; this proves only that arbitrary caller verifier minting is permitted by the type API. The candidate's fields are private and it has no public accessors, so an implementation in the Host crate cannot inspect principal, device, session, challenge-bound fields, or time to verify them. An external-consumer compile-negative tries `candidate.session_id()` and matches the actual missing-method diagnostic. Therefore an external Host-owned negative verifier matrix is blocked at the current API boundary; current in-crate `AcceptAuth`/`StaleAuth` fixtures only prove the policy crate's control flow and are not real authentication. No OS account/session, device key, challenge nonce, or revocation authority is established here.

### P — Provider

`CapabilityProvider` is publicly implementable by downstream crates and has default `health() = Ready`. The Host package is binary-only, so downstream crates cannot import its live registry, but can create arbitrary same-ID Provider instances. A new real `serea-capability` test builds two sequential `ProviderRegistry` values with equal `ProviderId`s and different `Arc` allocations, then confirms `Arc::ptr_eq` is false. This models replacement at the registry crate boundary; it does not prove Host lifecycle binding. The trait proves a provider port implementation, not that it is the exact Host-owned instance selected by a registry generation. No invoke is authorized by this evidence; Provider `invoke` remains out of scope.

## Public consumer probe already present in PR #33

`tools/p8b_authority_cargo_probe/run.py` compiles a real external Cargo package against Serea crates. Its positive probes import Storage snapshots and compose Grant use, directly call public `Tx::acquire_lease` with an arbitrary `LeaseOwner`, implement a verifier that always returns `Ok(())` and mint the `AuthenticatedApprovalResponseV1` wrapper, implement arbitrary `CapabilityProvider`, relabel public `PolicyEvaluation.decision`, and evaluate a supplied Policy input. Negative probes target private observation fields, SQL internals, the inaccessible approval-candidate session claim, and absent CommitProof/Permit types. Stable and Rust 1.85 runs both exit 0; two positive public-surface composition cases pass; all six negative probes match their expected privacy/absent-API diagnostics. These are the relevant attack classifications: durable lease acquisition is public; Grant consumption/event operations are public; an arbitrary verifier can mint the wrapper called authenticated; Policy explanation is caller-composable; arbitrary provider implementations are accepted by the port. None is an Invoke/Permit and none proves production dispatch.

The new `grant_fact_projection_does_not_reject_a_corrupted_sealed_member_set` fixture creates a Grant through the typed response writer and file-backed SQLite, then drops only the member/seal no-delete triggers in the explicitly adversarial corruption fixture and deletes the member. The existing public read returns `sealed=true`, `member_count=0`, `action_count=1`, and no selected-member digest rather than refusing. `verify_integrity()` passes after reopen. Grant-use count remains zero. The targeted test passed, and it also passed in the stable all-target/all-feature workspace suite. This demonstrates that the existing projection/structural check does not audit full-set integrity; it is not evidence that a normal typed write path can create the corruption.

RED/GREEN mutation was run in an isolated detached scratch worktree based on the exact PR #33 HEAD, with a separate test invocation against the real Storage/SQLite fixture. Changing the expected corrupted member count from 0 to 1 failed at the intended assertion (`left: 0`, `right: 1`); restoring the actual 0 expectation passed. This tests assertion detection only; it does not represent a production implementation fix.

## Current track status and blockers

| Track | Status | Evidence boundary |
|---|---|---|
| W | `W_PARTIAL` | Real API/source proves `LeaseGuard` row/origin fencing and public owner-string acquisition; Host-issued principal is not bound, and public acquisition is an explicit bypass. |
| T | `T_PARTIAL` | Real `BEGIN IMMEDIATE` closure ordering permits post-acquisition sampling; runtime callers still supply time; no host-owned clock witness/rollback policy. |
| G | `G_PARTIAL` | Real typed writer and SQLite trigger invariants bound normal membership (max eight); no complete-set read/recompute proof; seal is not a digest. |
| O | `O_BLOCKED` | External Host implementations can implement the verifier trait but cannot inspect private candidate claims; a specific external compile-negative confirms this. In-crate accept/stale fakes are fixture-only. |
| P | `P_INSTANCE_CANDIDATE_PARTIAL` | Public provider trait/default Ready permit caller-owned fake providers; exact Host Arc instance/lifecycle is not observed. |

No W/T/G Host authority API is added because the current dependency/visibility boundary cannot enforce it without a production API contract. No migration, Policy behavior, Provider dispatch, or public authorization API is changed. Next implementation should be an Owner-approved API boundary decision, then a narrow test-only complete-set reader in Storage and an isolated Host/Storage principal integration prototype whose adversarial external consumer explicitly tests current bypass removal. Keep L2, L3 and dispatch disabled.
