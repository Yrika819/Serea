# P7A owner decision package — Memory contract

**Status:** PREIMPLEMENTATION / PROPOSED; no decision below is ratified.
**Review state:** `P7A_P8A_OWNER_DECISION_PACKAGES_PREPARED`; this is a documentation-preparation label, not evidence of owner review, ratification, or implementation readiness.
**Severity key:** BLOCKER prevents the affected implementation; MAJOR is a high-risk contract choice; MINOR is bounded scope; NOTE records a known limitation.

This package separates accepted contracts, verified current behavior, proposed owner choices, and deferred work. It does not amend an Accepted ADR or authorize code or migrations.

## Accepted existing contract

- [ADR-0006](../decisions/ADR-0006-sqlite-fts5-memory.md) selects SQLite FTS5 for initial **lexical** retrieval, no vector database, explicit `EXTRACTION`, inherited source class, provenance, and target-platform FTS5 verification.
- [ADR-0010](../decisions/ADR-0010-data-classification-and-credential-exclusion.md) and [Data Classification §§2, 5, 7, 8](../protocols/09-data-classification-protocol.md#2-the-dataclass-set) require monotone derived classification, fail-closed handling of unknown values, credential exclusion, host-controlled extraction, immutable provenance, EventId-style Memory identity (`evt_` + ULID), and forget/tombstone semantics. [Model Protocol §3](../protocols/03-model-protocol.md#3-modelrequest) defines host-assigned `EXTRACTION` purpose and structured output; CHAT/ANALYSIS is not authority to write Memory.
- [Task Protocol §8](../protocols/02-task-protocol.md#8-task-retention-and-privacy) says ordinary Task expiry deletes task data but does not automatically delete independently retained Memory; explicit “forget this” deletes Task data and Memory derived from it. [Event Protocol §8](../protocols/06-event-protocol.md#8-retention) keeps its own event retention lifecycle. [Bounds Protocol §2](../protocols/10-bounds-protocol.md#2-the-bound-set) supplies existing task/event count, byte and batch-bound patterns; no Memory-specific item/byte quota is approved.
- [Crate Map](../architecture/03-crate-map.md#1-the-layering-rule) places `serea-memory` at L3 beneath `serea-task-engine`; Memory must not own Task sequencing or leases. No dependency cycle is allowed.
- Existing Blob identity is `(sha256(canonical plaintext), data_class_rank)`; class participates in both key and lookup. SECRET/CREDENTIAL are rejected. PRIVATE blob access is gated behind an `AtRestProtection` seam.

## Verified current implementation

1. `tasks` has no authoritative owner-user column or binding relation. `origin_device_id` is nullable and represents a device, not a durable user principal. A device can be replaced or shared; a user can have multiple devices.
2. `task_steps` cascades on Task delete. Existing receipt and approval rows are task-scoped. Memory tables and FTS schema do not yet exist; there is no Memory implementation to preserve.
3. [ADR-0022](../decisions/ADR-0022-durable-private-data-at-rest.md) remains **Proposed**. Storage rejects PRIVATE ordinary rows without protection, and complete ordinary-row encryption is unresolved. A test-only PRIVATE blob backend is not production protection. SECRET and CREDENTIAL are rejected.
4. `Store::transact_with_participants` coordinates transactional storage, journal and event participants. `BlobRef` is typed by exact class, and blob lookup uses both digest and class.
5. Existing migration identities 0001–0008 are recorded in [P6 post-merge verification](P6-post-merge-main-verification.md). Do not edit them. New schema must use additive migrations after owner-approved design.
6. ADR-0006 names FTS5. A temporary Python SQLite 3.53.1 experiment confirmed FTS5 module availability and a `unicode61` Japanese substring limitation: searching `予定` did not match a one-row fixture containing contiguous `予定を午後に変更`. This is a narrow observation from CPython SQLite, not a Rust `rusqlite` bundled-build portability result, corpus benchmark or quality score. No Japanese retrieval benchmark has been run.

## Proposed owner decisions

### P7-D01 — authoritative owner identity (**BLOCKER**)

**Question.** What stable identity owns a Task and every Memory derived from it, and how is that identity obtained from authenticated host context?

| Option | Benefits | Cost / risk |
| --- | --- | --- |
| **A. Add `task_owner_bindings(task_id PRIMARY KEY, owner_id, bound_at, binding_source)`** | Keeps Task wire shape and frozen migration history unchanged; gives Memory a stable owner-task composite parent key; allows future owner namespace without conflating device/session. | Requires one immutable binding per existing and new Task; historical rows need a justified single-user host identity and migration/backfill proof. Existing cross-task references must be audited. |
| B. Add `owner_id` to `tasks` in an additive migration | One direct owner field; straightforward Task query. | Alters core Task row and likely serialized Task model; backfill is still required; new composite references need a unique `(owner_id, task_id)` key; future owner transfer semantics become coupled to Task schema. |
| C. No owner field in V1 | Minimal schema now. | Cannot mechanically prevent cross-owner Memory reads/deletes. Only viable if owner is a single immutable host database identity passed to every access and there is no cross-owner data in a database; this invariant is currently unspecified. |

**Recommendation (proposed): Option A.** Define `OwnerId` as a stable host-authenticated principal identifier, independent of device/session IDs. Host authentication maps active user identity to OwnerId; device and session IDs are separate audit facts and never substitute for ownership. Bind owner at Task admission; no model-supplied owner, origin-device inference, or later silent transfer. V1 may have one owner per installation while retaining the explicit key for future migration.

**Historical Tasks.** Backfill only if the installation contract proves a single principal for the whole DB and maps it to a stable local owner ID. Do not infer the user from `origin_device_id`. If principal mapping cannot be proven, quarantine/unowned legacy Tasks from Memory extraction until an authenticated owner explicitly binds them. Binding table must be immutable and enforce exactly one binding per task.

**Cross-owner isolation.** Proposed parent keys include `UNIQUE(owner_id, task_id)`, `UNIQUE(owner_id, memory_id)`, and child references `(owner_id, task_id)` to that parent. All lookup, pagination, forget, FTS joins and blob-reference resolution take authenticated OwnerId in the same transaction/query. Do not accept an owner supplied by model output. Cross-owner composite key mismatch must be rejected by SQLite, not a caller convention.

**Migration/compatibility:** additive migration creates binding rows and indexes; historical backfill needs an operator-safe, deterministic rule. No owner key changes TaskId, EventId or DeviceId grammar. A later multi-user host may bind new owners, but the owner-identity issuer and transfer policy require a new owner decision before implementation.

### P7-D02 — Task expiry versus retained Memory (**BLOCKER**)

Ordinary Task expiry must not cascade to independently retained Memory. An explicit forget request must delete the appropriate derived Memory, provenance and derived descendants. A direct Memory FK to `tasks` with `ON DELETE CASCADE` contradicts Task Protocol §8; `ON DELETE RESTRICT` would block expected Task deletion.

**Recommendation (proposed):** Persist an immutable, content-minimized `memory_provenance` snapshot owned by the Memory record, with source TaskId/StepId, source capability/version, source event identity, extraction identity/time, source class and a source digest/reference. Preserve original TaskId and StepId as opaque historical identifiers **without a restrictive FK** after ordinary Task deletion. Verify all live references and source digest during extraction, then record the verification outcome in the immutable provenance snapshot and audit event. The Memory remains queryable and its provenance remains auditable after Task/Step deletion, while the audit explicitly indicates that the source row was later retained-out/deleted. Do not claim that a detached snapshot can revalidate deleted source bytes.

Explicit forget resolves by owner, item, source Task/Step/event, and the transitive supersession graph; then deletes selected Memory rows, provenance, FTS rows and now-unreferenced content. It must not erase unrelated Memory merely because it shares a Task or Blob. Task retention continues deleting Task/Step and task-scoped artifacts without deleting independent Memory. A cross-phase deletion event uses stable IDs and content-free counts; its transaction is atomic with Memory/FTS/tombstone state.

### P7-D03 — conceptual schema and constraints (**MAJOR**)

The following is a design sketch, not executable SQL. Every composite FK must target a declared primary/unique key with the same column order and collations.

| Relation | Proposed columns / constraints |
| --- | --- |
| `task_owner_bindings` | `task_id PRIMARY KEY`; `owner_id NOT NULL`; `UNIQUE(owner_id,task_id)`; immutable owner binding; host-authenticated binding timestamp/source code. The binding is a historical identity record, not a cascading child of `tasks`: a trigger validates that the Task exists when the binding is first inserted, while the row is retained as long as retained Memory/provenance refers to it. GC removes it only after the Task is gone and all retained references/tombstone obligations expire. |
| `memory_items` | `memory_id TEXT PRIMARY KEY` validated as `evt_` ULID; `owner_id`; kind (`WORKING`/`EPISODIC`/`SEMANTIC`/`PREFERENCE`); stored and transit class ranks; `content_digest`, `content_class_rank`, optional `BlobRef`; extraction TaskId/StepId; source capability/version; source EventId; created/expiry timestamps; optional supersedes ID; state; canonical metadata. `UNIQUE(owner_id,memory_id)`. Class monotonicity and allowed classes enforced by CHECK and host validation. |
| `memory_provenance` | one immutable row per `memory_id`; owner, extraction task/step, source EventId, capability/provider identity, source and extraction digest references, extraction/model identity and time, source/derived classes, redaction/projection metadata. Composite FK `(owner_id,memory_id)` to `memory_items(owner_id,memory_id)` with cascade on explicit Memory deletion. No FK to Task/Step that makes Task retention erase or block Memory. |
| `memory_supersessions` | `(owner_id, old_memory_id, new_memory_id)` with `UNIQUE(owner_id,old_memory_id)` if one successor is the selected V1 rule; both endpoints composite-FK to unique `(owner_id,memory_id)`; no self-edge; immutable links. Host transaction walks ancestors/descendants with a bounded recursive CTE and refuses cycles; SQLite recursive trigger/check design must be proven before implementation. |
| `memory_forget_tombstones` | random tombstone ID; owner; opaque source EventId/StepId or provenance ID; deletion time/reason code; suppression policy/version; content-free, no statement or plaintext digest. Unique key on owner + source identity + extraction contract where policy requires duplicate suppression. Retention lifetime is owner decision P7-D07. |
| `memory_fts` | FTS5 rowid tied to Memory internal rowid or stable opaque mapping; index only eligible PUBLIC/PERSONAL projections; atomic insert/update/delete with content table in one SQLite transaction; content-free trigger/repair policy documented. FTS is derived and rebuildable. |

Proposed supporting indexes: `memory_items(owner_id,kind,retention_expires_at_ms,memory_id)`, `memory_items(owner_id,created_at_ms,memory_id)`, `memory_provenance(owner_id,source_event_id,extraction_task_id,extraction_step_id)`, a partial GC index on expiry for eligible active rows, and unique owner/source/extraction-contract tombstone lookup. Exact column names and partial predicates must match final schema and query plan; all search predicates still recheck authoritative rows.

Blob FK: `(content_digest, content_class_rank)` references `blobs(digest,data_class_rank) ON DELETE RESTRICT`, exactly preserving the existing two-column identity. A Memory reference must not look up by digest only, lower the class, or claim that a PRIVATE Blob is protected merely because `protection='AT_REST'`. `UNIQUE(owner_id,task_id)` from the retained historical binding table and `UNIQUE(owner_id,memory_id)` are the required parents for owner composite FKs. The owner-task binding must outlive ordinary Task deletion while Memory refers to it; do not cascade-delete that parent. A bounded GC later deletes an unreferenced binding only after its retention/tombstone obligations end. Avoid a composite FK to `(task_id,step_id)` unless a matching unique parent key is added in an additive migration; legacy `task_steps` does not expose that exact composite key today. The recommended detached provenance intentionally has no such live FK.

**Supersession cycle prevention:** application-only validation is insufficient against concurrent writers. Serialize graph mutation in one immediate SQLite transaction, enforce a single canonical successor rule if selected, and run a bounded reachability check before insert; require property/concurrency tests showing A→B then B→A is rejected across independent connections. Alternative is immutable parent pointers with one parent per item and transactionally checked ancestors. The owner must select branch/fan-out semantics before migration.

### P7-D04 — privacy at rest (**BLOCKER for PRIVATE activation**)

| Option | Consequence |
| --- | --- |
| **A. Initial PUBLIC/PERSONAL only; PRIVATE pathways fail closed** | Makes a bounded V1 possible without pretending ADR-0022 is complete. External Gmail/calendar/notification content currently classifies PRIVATE; it cannot be persisted as Memory under this option unless a previously defined, host-approved redacted projection has a justified lower stored class (redaction alone does not lower stored class). |
| B. PRIVATE Blob only with additional restrictions | Existing seam/test wiring does not protect Memory metadata, provenance, FTS, tombstones, WAL, logs or ordinary rows. Not sufficient for PRIVATE Memory activation. |
| C. Complete production PRIVATE encryption and ordinary-row protection before activation | Stronger support, but requires a real reviewed platform key backend, encrypted row/index representation, key rotation/recovery and audit before the phase can accept PRIVATE. |

**Recommendation (proposed): Option A.** Memory stored class inherits the highest source/derived class; PERSONAL content may be stored subject to user consent and retention. PRIVATE content and metadata that classifies as PRIVATE fail closed until full production row/blob/WAL/backup/FTS protection is implemented and audited. SECRET and CREDENTIAL never enter ordinary Memory, provenance, event, FTS, logs or ActionResult. Provenance and metadata are classified independently and at least as high as the data they identify; source names, account identifiers, titles and stable digests can themselves be sensitive. Never put PRIVATE searchable plaintext into FTS.

### P7-D05 — retention and capacity candidates (**MAJOR**)

The following are candidates only, not defaults approved by this package: WORKING 7 days; EPISODIC 90 days; SEMANTIC 365 days; PREFERENCE 365 days with explicit renewal. Proposed policy requires expiry visible to the user, immutable creation time and current expiry, and an explicit authenticated user renewal action; model retrieval or repeat extraction cannot renew. Renewal should create an audit event and may not exceed a separately ratified maximum horizon.

Before implementation select: max items per owner and kind, max bytes per owner and item, max retention extension and renewal cadence, FTS bytes, tombstone quota/lifetime, and GC batch/continuation semantics. Exhaustion fails closed and reports a bounded typed error; it never silently evicts non-expired Memory. GC deletes only expired, unreferenced objects in bounded transactions, preserves shared BlobRefs while any owner-visible item or other durable row references `(digest,class)`, and does not imply Task deletion. Source deletion/retention and Memory deletion are independent; record source no-longer-present without rewriting immutable provenance. Event retention remains governed by Event Protocol.

### P7-D06 — FTS5 / Japanese lexical retrieval (**MAJOR**)

ADR-0006 selects FTS5 but does not prove every bundled SQLite target has the feature or establish Japanese quality. Verify the actual `rusqlite` bundled SQLite compile configuration and `SELECT sqlite_compileoption_used('ENABLE_FTS5')` / module availability on Linux, Intel macOS, arm64 macOS and future Android/macOS builds. A deterministic test must create/search an FTS5 table, exercise rollback, rebuild, and `integrity-check`.

FTS5 `unicode61` tokenizes Unicode word characters and has no Japanese morphological segmentation. Japanese without spaces can behave as long tokens, so lexical substring recall may be poor; this is a theoretical limitation, not benchmark evidence. Alternatives: trigram tokenizer for substring matching (larger index, short-query edge cases, privacy leakage); host-side reviewed Japanese tokenizer/token stream (new code and versioned index rebuild); retain FTS5 as lexical baseline and defer semantic/vector search. No option may claim semantic similarity from FTS rank. Search is owner-filtered and class-filtered before returning content, validates query length/token count/operator syntax, bounds page size and work, uses parameter binding, and has stable ordering `rank, created_at_ms, memory_id` with the precise rank direction frozen. A continuation cursor should bind owner, query digest, filter, sort tuple and snapshot/generation; if a stable snapshot cannot be guaranteed, explicitly define pagination as best-effort across mutations.

External-content FTS trigger maintenance must be in the same SQLite transaction as the content row. FTS is a derived index: migration/rebuild path, `integrity-check`, mismatch detection and repair are mandatory; failure blocks search or rebuilds, never falls back to an unclassified scan. Filter class on the authoritative row in the same query, not only in FTS. Benchmark evidence is currently **none**; record representative Japanese fixtures, platform, build, exact query set, latency, recall and index bytes before approving tokenizer choice.

### P7-D07 — forget, tombstones, backup recovery and poisoning (**MAJOR**)

**Recommendation (proposed):** authenticated host resolves target under OwnerId; verify current item and owner; compute transitive supersession closure with a cycle guard; in one transaction delete selected Memory, provenance, eligible FTS rows and unshared content references, insert content-free tombstones, and append a content-free event with stable identifiers/counts. Shared Blob rows are deleted only by reference-aware GC after all references are gone. Repeated forget is idempotent and returns an auditable outcome. Do not claim physical secure erase: SQLite pages, WAL, snapshots and backups may retain old bytes.

Tombstones must suppress source-event re-extraction after restart and backup restore. Avoid unkeyed SHA-256 of short/guessable Memory text: an attacker with a DB copy can dictionary-test common preferences. Prefer a random opaque Memory/provenance identifier and source event identity; if content-equivalence suppression is required, use a keyed, rotatable HMAC held outside SQLite and define backup/key-loss behavior. Never store deleted text or an unkeyed content digest in tombstones. Tombstone retention/scope is an owner decision: indefinite suppression gives strongest resurrection defense but unbounded metadata; bounded suppression limits storage but eventually allows re-extraction. Backup restore must replay durable tombstones newer than the snapshot from a separately retained deletion ledger or fail closed until reconciled; same-DB WAL checkpoint is not a backup-erasure guarantee.

RED-first tests: forged provenance IDs; cross-owner fetch and forget; source class downgrade; model-produced instruction/policy strings in Memory; extraction from CHAT/ANALYSIS; fabricated/incorrect source EventId/capability; supersession cycle and concurrent cycle; tombstone bypass and post-restore re-extraction; unshared/shared Blob deletion; FTS stale-row leak after delete/class change; owner/class filter bypass; PRIVATE/SECRET/CREDENTIAL extraction refusal; Task expiry retaining Memory but explicit forget removing it. External source text is untrusted data forever; it can never set policy, owner, capability, approval, retention or host instructions.

## Alternatives, impacts, exit criteria

| Decision | Migration | Compatibility | Operational / security consequence |
| --- | --- | --- | --- |
| P7-D01 owner binding | Add binding relation and deterministic backfill or quarantine | Task wire IDs unchanged; host calls gain authenticated OwnerId | BLOCKER until stable identity and legacy policy are selected; prevents cross-owner aliasing |
| P7-D02 provenance detach | Add immutable provenance snapshot and references | Task may expire while Memory remains; “forget Task” remains explicit broad delete | BLOCKER; no accidental Task cascade, but deleted source can no longer be independently re-read |
| P7-D03 schema/supersession | Additive tables, unique parent keys, indexes and FTS | `evt_` identity remains; no migration 0001–0008 edits | MAJOR; owner/class keys must be mechanical and all FKs valid |
| P7-D04 class ceiling | CHECKs and write/query filters | PRIVATE content is unavailable in V1 | BLOCKER to PRIVATE activation; aligns with ADR-0022 fail-closed baseline |
| P7-D05 limits | Additive host config/bounds and GC cursor | Expiry becomes user-visible contract | MAJOR; numeric defaults are not yet measured/approved |
| P7-D06 index | FTS virtual table plus maintenance/rebuild/integrity | Lexical only; tokenizer version is persisted contract | MAJOR; Japanese quality and index confidentiality need evidence |
| P7-D07 deletion | Tombstone and event lifecycle, recovery hooks | Forget results are idempotent; backups may retain old pages | MAJOR; suppression lifetime and key/backup recovery need owner decision |

**Severity disposition:** D01, D02 and PRIVATE activation under D04 are BLOCKER. D03, D05, D06 and D07 are MAJOR contract choices. The default lexical FTS query grammar/pagination encoding is MINOR within the selected P7-D06 tokenizer decision, but resource bounds and owner/class filtering are not minor. Existing no-production-PRIVATE statement and the CPython-only FTS probe are NOTEs, not security guarantees.

### Phase gates (proposed; no implementation gate is complete)

**P7A — contract ratification gate.** P7A is complete only when the owner has reviewed and either ratified or explicitly deferred each D01–D07 choice, with a fail-closed scope for any deferral. Specify the authenticated OwnerId source and legacy Task backfill/quarantine policy; Task expiry versus independently retained Memory; PRIVATE scope; conceptual schema, unique parent keys and supersession semantics; numeric retention/capacity defaults or explicit deferred values with fail-closed behavior; FTS tokenizer/query semantics or a bounded preliminary lexical baseline; forget/tombstone/backup-restore contract; and RED-first test requirements. Identify any Accepted ADR or frozen protocol amendment separately for explicit approval. These are contract decisions and conceptual review criteria; P7A does **not** require P7B–P7E code or tests to exist or pass.

**P7B — schema implementation gate.** Before treating the schema slice as validated, require real additive migration validation; SQLite proof that every composite FK references a matching UNIQUE/PRIMARY KEY parent with the same columns and order; runtime foreign-key/integrity tests; owner binding, legacy quarantine, Task-expiry/Memory-retention and forget tests; actual FTS5 availability on each supported SQLite build; and migration, rollback and fault-injection validation. No P7B gate is complete in this package.

**P7C–P7E — runtime and adversarial closure.** Require implemented host-authorized extraction and classification inheritance; owner/class search isolation; representative Japanese retrieval evaluation; forget, tombstone and supersession correctness; backup/restore and restart recovery; bounded retention GC; cross-platform portability; and independent adversarial review. No P7C–P7E gate is complete here.

These are distinct evidence levels: **owner approval** selects the contract; **conceptual proof** reviews invariants and proposed relationships; **executable migration proof** tests actual DDL and key constraints; **runtime implementation validation** tests real behavior; **production readiness** additionally requires adversarial, recovery, portability and operational evidence. None implies the next level automatically.
