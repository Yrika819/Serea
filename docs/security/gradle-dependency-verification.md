# Gradle dependency verification — SEC-A2

## Decision

Do not activate Gradle dependency verification yet. Gradle uses one verification file for the Android build, including plugin resolution, and a file at `android/gradle/verification-metadata.xml` activates strict verification. The audit found dependencies whose candidate hashes are absent or lack independently trusted provenance. Enabling a partial file would make unrelated builds fail or would require trust exceptions that hide unchecked artifacts.

The generated metadata is kept as an inactive evidence file at [`evidence/gradle-8.14.6-generated-candidate.xml`](evidence/gradle-8.14.6-generated-candidate.xml). It is not in Gradle's activation path. Its `Generated by Gradle` hashes are candidate values, not approved trust roots.

## Baseline and Gradle 8.14.6 behavior

This audit uses PR #82 HEAD `316f19ccc66af4a27d7514d6510f108de6452172`. The Android wrapper requests Gradle 8.14.6 and pins distribution SHA-256 `7988ed071b2a07900e2ec715fca15c6ab72bce6db433af301fa7fa7e9407bd24`. The wrapper value matched the official `gradle-8.14.6-bin.zip.sha256`, and the downloaded distribution matched it as well.

Gradle enables dependency verification when it finds `gradle/verification-metadata.xml` at the build root. One file covers projects, plugins, build logic, and plugin dependencies. It can check artifact and metadata checksums, and PGP signatures. An artifact missing from the metadata or whose bytes do not match a listed checksum fails verification. Gradle's own guidance says generated metadata must be reviewed because dependencies already compromised during bootstrapping would otherwise be trusted. See the [Gradle 8.14.6 dependency verification guide](https://docs.gradle.org/8.14.6/userguide/dependency_verification.html).

The current [`android/app/gradle.lockfile`](../../android/app/gradle.lockfile) has 324 unique locked coordinates and covers app configurations. The app build enables `lockAllConfigurations()`, but Gradle documents that project locking does not lock buildscript classpaths. The lockfile records selected versions; verification metadata records approved artifact bytes and signatures. One does not replace the other. See [Gradle dependency locking](https://docs.gradle.org/8.14.6/userguide/dependency_locking.html).

No sidecar mismatches were observed. Repository-hosted SHA-256 values are useful official checksum evidence, but they share a trust boundary with the artifact repository and do not by themselves protect against that repository being compromised. The [Android Developers Jetpack signature guidance](https://developer.android.com/jetpack/getting-started#verify-jetpack-dependencies) publishes four Google signing-key fingerprints. Using those fingerprints, 35 AndroidX JAR/AAR signatures were cryptographically verified; 47 AndroidX binary files had no signature. Signatures for other publishers, and signatures on metadata files, remain unaudited. The 35 verified signatures are binary-file evidence and do not raise a component's status unless its other candidate files are also covered.

The inventory includes the five declared plugins and their resolved marker/implementation coordinates: Android Gradle Plugin 8.12.3, Kotlin Android 2.4.21, Kotlin Compose 2.4.21, KSP 2.3.12, and dependency-license-report 3.1.4. The metadata candidate contains plugin classpath dependencies that are absent from the app lockfile.

## Reproducible audit and negative tests

`tools/audit_gradle_dependency_candidates.py` regenerates the CSV. It checks each candidate hash against published `.sha256` sidecars when requested, and optionally verifies AndroidX binary signatures against Android Developers' published full fingerprints. It does not label a generated value as verified just because Gradle generated it.

```sh
python3 tools/audit_gradle_dependency_candidates.py \
  --check-official-sidecars \
  --verify-androidx-signatures
```

`tools/test_gradle_dependency_verification.sh` creates isolated local Maven fixtures. It runs a valid-checksum control and requires Gradle 8.14.6 to reject an unregistered dependency, a wrong SHA-256, and an artifact modified after its approved hash was written. These tests validate Gradle's enforcement behavior; they do not validate the Serea dependency graph.

```sh
tools/test_gradle_dependency_verification.sh
```

## Staged adoption and second review

1. Resolve every configuration used by plugin/buildscript resolution, Android runtime, unit tests, instrumentation compilation and execution, license reporting, and IDE sync. Refresh the candidate only after recording the exact Gradle version, tasks, lockfile, repositories, and resolved coordinates. Include detached/task-internal configurations such as the 10 Android Test Platform coordinates above.
2. For each candidate artifact and each POM or `.module` file, obtain an official checksum from a trusted publication channel or verify its publisher signature against a fingerprint published outside the artifact repository. Check the downloaded bytes against the evidence. A `.asc` file's presence alone does not establish publisher identity.
3. Have a second reviewer independently retrieve the checksum or public key evidence and recompute signature/hash results. Review additions, removals, versions, artifact filenames, metadata files, signer fingerprints, and trust scopes against the dependency graph. Do not accept a hash solely because it appeared in Gradle's generated diff.
4. Only after every resolved artifact has reviewed evidence, add the file at `android/gradle/verification-metadata.xml` with metadata verification enabled and signatures enabled for trusted keys. Keep unknown dependencies and checksum mismatches fatal. Do not add broad `<trusted-artifacts>`, ignored keys, lenient verification, or standing exceptions.
5. For dependency updates, make the lockfile and verification metadata changes in a dedicated reviewable change. The author regenerates a candidate from a clean cache; the second reviewer independently checks the exact additions against publisher evidence. Run the negative tests and all required Gradle configurations before accepting the update.

## Residual risks

- Dependency verification is not active; Gradle currently does not reject changed or unregistered Android dependencies based on this candidate.
- 273 of 502 inventory components are incomplete or unverified by the checksum-sidecar review, and 10 locked Android Test Platform components have no generated hashes.
- 35 AndroidX binary signatures were checked against published Google fingerprints; publisher signatures for the remaining artifacts and signatures on POM/module metadata were not fully checked.
- A checksum sidecar served by the same repository does not independently authenticate that repository. Independent publisher signatures or checksums from a separate trusted channel are still needed for the remaining scope.
- The app lockfile does not pin the root plugin/buildscript classpath. Verification metadata is intended to cover those bytes once the full global inventory is ready; it is not a substitute for plugin version locking.
- The negative tests exercise Gradle's local verification behavior, not a full Android build, emulator run, or all task-specific configurations.

No `android/gradle/verification-metadata.xml` is active, no Gradle trust exception was added, `SECURITY.md` was not changed, and no settings, UI, or harness implementation files were modified.
